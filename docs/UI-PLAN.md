# 専用 Web UI（AI-PMO Console）の実装計画 / Plan for the dedicated web UI

画面案（デザインキャンバス: 今日・タスク・WBS・受信箱・成果レビュー・自律的な判断・メンバーと学習・連携・スマホ）を、
**既存の Web（`aipmo serve`）に取り込む**ための計画です。既存の API でできる範囲、足す API、順序と判断が要る点を、
実際のコードに当てて洗い出しました。**第 6 章のとおり、すべて実装済み**です。

The mockups become the existing web (`aipmo serve`) step by step. This lists what the existing `/api` already
covers, what to add, the order, and the decisions needed. Everything in chapter 6 is implemented.

## 1. 設計の原則（画面案から）

1. 人の判断（承認・確定・レビュー・起票）は**受信箱**に集める。
2. **理由を必ず見せる**（点数の内訳・診断の根拠・過去の成功率）。
3. 実行は承認のあと。**外の世界に書く操作は、押したときだけ**。
4. 読むだけの所と書ける所を、画面でも分ける（WBS は読むだけ）。
5. **書き込みの入口を増やさない。** 画面は既存の `/api/pmo/...` を呼ぶ。新しい API は、原則として**読むだけ**。

## 2. いまの Web

- ビルド工程なし（素の JS/CSS）。1 ページ（`index.html` + `app.js` + `app.css`）に、PMO Core・WBS 再計画提案・
  テンプレート・実行が縦に並ぶ、スマホ向けの画面。
- 認証: トークン（operator / viewer）。viewer は `web.viewer_projects` でプロジェクトを限定できる。
- 台帳への接続は上限つきのプール（`web.pool`）。表示は読み取り、書き込みは operator のみ。

| 既存の API | 返すもの |
|---|---|
| `GET /api/pmo` | ブリーフィング（警告・担当の提案・上位 10 件・プロジェクト・メンバーの負荷・学習・自律的な判断・収集）、上位 50 件のタスク（理由つき）、承認待ちの提案、起票待ち、レビュー待ち |
| `GET /api/pmo/decisions` | 判断ログ（新しい順、プロジェクトで絞れる） |
| `POST /api/pmo/proposals/decide` | 提案・判断の承認／却下 |
| `POST /api/pmo/assignments/accept` | 担当の確定（書き戻しは任意） |
| `POST /api/pmo/agents/review` | 役割AIの成果の認める／差し戻す |
| `POST /api/pmo/filing` | 起票／見送り |
| `GET/POST /api/wbs-proposals…` | WBS 再計画案（PostgreSQL）の一覧・承認・却下（承認で WBS ファイルへ反映） |
| `GET /api/health` | アダプタの疎通、台帳プールの状況 |
| `GET /api/session` | 役割・テナント・文言・書き戻せるトラッカー |
| **`GET /api/inbox`（新）** | 人の判断を待つもの全部（5 章） |

## 3. 画面ごとの対応

凡例: ✅ 既存の API で足りる ／ 🔶 読み取りの API を足す ／ ✍ 書き込みの API を足す

| 画面 | 既存で足りるもの | 足すもの | 区分 |
|---|---|---|---|
| **受信箱** | — | `GET /api/inbox`、各項目の `actions` から既存の書き込みを呼ぶ | ✅ **実装済み** |
| **今日** | `/api/pmo`（全体のレベル・KPI・警告・プロジェクト・負荷・学習・上位）、`/api/inbox` の件数 | なし。KPI は画面で数える | ✅ |
| **タスク** | `/api/pmo` の上位 50 件と `reasons`（点数の内訳の文字列） | `GET /api/tasks`（絞り込み・並び・ページ）、`GET /api/tasks/{id}`（履歴・役割AIの実行・関連する警告と提案）。内訳を**構造化**（`[{label, points}]`）して返す — 今は文字列（`優先度 Highest +40`）なので、`score_task` が項目ごとの点数も返すようにする | 🔶 |
| **WBS** | 更新漏れ・証拠の欠けは受信箱に出る。`wbs status --json` は集計（進捗・速度・見込み・クリティカルパス・次に着手できる） | `GET /api/wbs`（設定の WBS ファイルを `analyse` した結果）。**ツリー**（子・見積り・担当・期限・依存・証拠の有無・完了日）を返すよう `analyse` を拡張する。PR コメントの本文のプレビュー（`wbs_notify.render`）は任意 | 🔶 |
| **WBS: 再計画案の承認** | `/api/wbs-proposals…`（承認で反映）。受信箱にも出る | 変更の一覧（`diff.changes`）と**反映後の差分プレビュー**を返す `GET /api/wbs-proposals/{id}/preview`（`wbs_proposals.plan_for` をそのまま使う。書かない） | 🔶 |
| **成果レビュー** | 受信箱の `review` 項目、`POST /api/pmo/agents/review`、ブリーフィングの `agents`（認めた／差し戻し／待ちの件数） | 確かめ済みの履歴（誰が・いつ・メモ）の一覧 `GET /api/agents/reviews`（判断ログの `agent_reviewed` から） | 🔶 |
| **自律的な判断** | ブリーフィングの `judgment`（診断・自律度・一時停止・遮断器・直近）、承認は受信箱 | 一時停止／再開／遮断器の解除 `POST /api/judgment/{pause,resume,reset}`（制御の文書に書く。operator のみ）。**自律度の変更は別の判断が要る（6 章）** | ✍ |
| **メンバーと学習** | `/api/pmo` の `member_loads`・`learning` | メンバーごとの実績の集計（件数・平均の遅れ）`GET /api/learning/members`。補正の根拠を見せるため | 🔶 |
| **連携** | `/api/health`（アダプタ・プール）、ブリーフィングの `collection`、起票待ちは受信箱 | `GET /api/integrations`（収集の最終結果・WBS ファイルの検証結果・担当アカウントの対応表 = `AssigneeResolver`）。「今すぐ収集」は書き込みではない（読み取り専用の収集）が、常駐の仕事なので**ボタンは置かない**（`aipmo collect`） | 🔶 |
| **スマホ** | 同じ API。幅で配置を変えるだけ | なし | ✅ |

新しい API は、**書き込みが 1 つ（判断の一時停止など）だけ**で、残りは読み取りです。

## 4. 画面の骨格（シェル）

- **画面の切り替え**: 左のサイドバー（広い画面）／下のタブ（スマホ）。URL のハッシュで画面を持つ
  （`#inbox` `#wbs`…）ので、リンクで共有でき、戻るボタンが効く。受信箱では、タブとハッシュを**すでに実装**した。
- **見た目**: 既存のトークン（`--surface` `--ink` `--accent`…）を使い、ダークモードにも追従する。画面案の
  サイドバー・カードの形に、段階的に寄せる。旧画面（PMO Core・WBS 再計画提案・テンプレート・実行）は、
  **置き換えが済むまでタブとして残す**。
- **更新**: 画面に戻ったとき（`visibilitychange`）と、操作のあとに読み直す。定期のポーリングはしない（電池）。
  常駐の周に合わせて自動で更新したくなったら、サーバー送信イベント（SSE）を別途検討する。
- **文言**: 画面の文言は 8 言語（`aipmo/i18n.py`）。サーバーが返す理由の文章（「承認すると…」など）は、**今は日本語のみ**
  （他の言語に切り替えるには、`/api/inbox` が文言のキーと値を返す形にする必要がある — 7 章）。
- **アクセシビリティ**: 本物のボタン・ラベル・`aria-pressed`/`aria-current`・フォーカスの移動。色だけで区別しない
  （種類は文字のラベルつき）。
- **ビルド工程は持たない**（素の JS）。画面が増えて `app.js` が大きくなったら、`<script type="module">` で分割する。

## 5. 実装済み: 受信箱（フェーズ 1）

| | |
|---|---|
| API | `GET /api/inbox`（[aipmo/inbox.py](../aipmo/inbox.py)）。種類: 判断・対応・WBS・担当・成果・起票・再計画案。緊急度順、同じなら古い順 |
| 読むだけ | 台帳を変えない。決める操作は、各項目の `actions` が指す既存の API |
| 権限 | viewer には `actions` を返さない。プロジェクトを限定された viewer には、組織全体の項目（判断・起票・再計画案）を出さない |
| 画面 | 種類のフィルタ、一覧、詳細（診断の根拠・選んだ対処・**承認すると／しないこと**）、決めると次の項目へ、差し戻しは理由が必須、↑↓ で移動、スマホは縦に積む |
| テスト | サーバー側 20 件（デモのデータで 14 件が集まる／各 action がそのまま動く／全部決めると空になる…）と、**実ブラウザ（Chrome）** での操作 1 件（`AIPMO_TEST_BROWSER=1`） |

実ブラウザの確認では、スマホ幅（390px）で横にはみ出さないこと、承認で件数が 14 → 13 になること、理由なしの差し戻しが
止まること、タブの切り替え、viewer にボタンが出ないことを確かめた。

### 実装で決めたこと・分かったこと

- **点数の内訳**: 内訳の合計は台帳の点数と一致する。画面の台帳には常駐が学習した補正が載っていないので、`pmo-learned` を
  読んで再計算し、それでも差が出たときは隠さず「その他の補正」の項目として出す。
- **判断の操作は「依頼」**: 一時停止・再開・遮断器を戻すは制御の文書に書くだけで、常駐が**次の周**で読む。画面は
  「依頼済み（次の周で反映）」を出す。判断ログに `judgment_control` として残す。自律度は画面から変えない。
- **範囲を限られた viewer**: WBS・メンバーと学習・連携（組織全体の情報）は 403、タスク・成果の履歴は範囲内だけ。
- **WBS の予測**: 証拠の欠けなどの「誤り」があると、既存の判断どおり予測と順序を出さない。画面もそう出す。
- **工程バー**: WBS に開始日は無いので、終わり（完了日、無ければ期限）と、依存先の終わりの最も遅い日から描く。日付が無い作業には描かない。
- **関数名の衝突**: `app.js` は 1 ファイルなので、同名の関数が後のもので前のものを黙って上書きする（実際にタスク画面が旧い
  PMO 画面を空にした）。`tests/test_static_app.py` が重複を止める。

### 残っていること

- **多言語化の範囲**: サーバーが毎回組み立てる文章（受信箱の見出し・操作・「承認すると／しないこと」、点数の内訳、
  WBS の注意と証拠の確認結果）は、サーバーの言語（`lang`）で 8 言語に対応した（`aipmo/messages.py`。キーごとに
  8 言語、差し込みは全言語で同じ。`tests/test_messages.py` が確かめる）。**台帳やブリーフィングに保存された文章**
  （警告・診断のタイトルと根拠・提案のタイトルと理由・担当の提案の理由・タスク名・成果の要約）は、書いた時点の言語のまま出る。
  再計画案の反映プレビューの変更点の文（`wbs_edit` の report）、WBS ファイル自体の構造の誤りの文も日本語のまま。
- ブラウザは Chrome（ヘッドレス）だけで確認。Safari・Firefox・実機のスマホは未確認。
- 画面の WBS は読むだけ。WBS の変更は再計画案の承認（PostgreSQL が要る）からのみ。
- 常駐の周（`aipmo schedule`）を待たずに画面を自動更新する仕組み（SSE）は無い。画面に戻ったときと操作のあとに読み直す。

## 7. 判断が要ること

1. **自律度（`off / propose / auto`）を画面から変えるか。** 今は `config.yaml` が唯一の正で、変更は再起動で反映される。
   画面から変えるなら「実行時の上書き」を持たせる必要があり、**安全の設計**（誰が・いつ・どこまで）が増える。推奨:
   **最初は表示と一時停止／遮断器の解除だけ**（設定の変更は `config.yaml`）。
2. **サーバーが返す理由の文章の多言語化。** 日本語のままで始めるか、キーと値で返すか。推奨: 日本語で始め、要望が出たら
   キー化（`/api/inbox` の `detail` を `{key, params}` にする）。
3. **旧画面の扱い。** 置き換えが済むまでタブで残す（推奨）か、早めに消すか。
4. **サイドバーのシェルを先に入れるか、WBS 画面を先に作るか。** 推奨: **シェルと「今日」→ WBS**（WBS は新しい API も画面も大きいので、
   骨格が固まってから）。

## 8. リスク

- WBS のツリー描画（工程バー・依存の矢印）は、画面案どおりにすると JS が大きくなる。まず表＋バーだけにして、矢印は後。
- 実 PostgreSQL・実 Jira・実ブラウザ（他のブラウザ・実機のスマホ）での確認は、今回は **Chrome（ヘッドレス）とデモのデータ**まで。
- 画面が増えると、`/api/pmo` が重くなる。画面ごとに必要な分だけ読む API に分けているのは、そのため。
